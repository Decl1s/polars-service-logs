# Конспект: JSONL-журналы, выражения Polars и почасовая витрина

Проект от 15 октября 2026 года. Версия 0.1.0.
Главный новый инструмент — Polars 2.0.0, язык — Python.
[Установка и запуск](README.md) · [Все технологии](TECHNOLOGIES.md).

## 1. Задача простыми словами

Есть журналы трёх вымышленных сервисов: api, worker и gateway. Каждая строка описывает
один запрос: когда пришёл, какой сервис ответил, какой HTTP-статус вернул и сколько
миллисекунд потратил. Нужно понять, в какие часы сервисы ошибаются и замедляются.

Вход содержит повторы и неправильные значения. Если посчитать всё подряд, один запрос
попадёт в статистику дважды, отрицательная задержка улучшит среднее, а неизвестный сервис
создаст лишнюю группу. Поэтому аналитика начинается с определения допустимых данных.

Результат — очищенные Parquet-файлы по дате UTC, почасовая таблица, причины отклонения
и русский Markdown-обзор. Это небольшой файловый конвейер, которому не нужен сервер базы.
У него нет связи с настоящими пользователями: генератор не создаёт IP, URL, cookies и контакты.

## 2. Отличие от предыдущего подхода

В этом проекте нет таблицы контрольных точек загрузки или накопительной истории.
Каждый запуск читает текущий набор файлов и заново строит **полный снимок**.
Если источник убрали из входной папки, его события исчезнут из следующего результата.
Повторный запуск даёт те же показатели, потому что не дописывает данные к старой выгрузке.

Такой вариант проще для небольшого периодического набора. Инкрементальная обработка
сэкономила бы чтение старых файлов, но потребовала бы правил исправления, удаления,
контрольных точек и восстановления истории. Выбор определяется договорённостью источника,
а не тем, какой способ выглядит сложнее в портфолио.

## 3. Что такое Polars и ленивый план

Polars предоставляет таблицы DataFrame и выражения для преобразования столбцов.
Основная работа выполняется бинарным движком; Python описывает операции и управляет файлами.
Например, `pl.col("status_code") >= 500` — описание вычисления признака ошибки сервера.
Оно применяется ко всему столбцу без написанного вручную Python-цикла по запросам.

`LazyFrame` хранит план. `scan_ndjson` задаёт источник, `with_columns` — новые поля,
`group_by` — группировку, а `collect` запускает вычисление. В проекте явно используется
`collect(engine="streaming")`. При этом результат collect всё равно оказывается в памяти,
а дедупликация и группировки требуют состояния. Название движка не означает, что весь
наш конвейер умеет обрабатывать неограниченный объём.

Перед Polars есть дополнительный проход Python по JSON. Он проверяет строгую структуру
и типы. Это осознанная цена учебной безопасности: источник читается больше одного раза.
Поэтому нельзя делать вывод о максимальной скорости Polars по скорости всего проекта.

## 4. Контракт одной записи

В JSONL одна непустая строка содержит отдельный объект. Обязательные бизнес-поля:
`event_id`, `timestamp`, `service`, `status_code`, `duration_ms`.

```json
{"event_id":"LOG-00000001","timestamp":"2026-10-01T10:15:00Z","service":"api","status_code":200,"duration_ms":125.5}
```

`status_code` должен быть целым JSON-числом, `duration_ms` — конечным числом.
Строка `"200"` и число `200` имеют разные типы. Логическое значение `true` тоже нельзя
принять за единицу, хотя в Python bool связан с int. Поэтому проверка использует
`type(value) is int`, а не только `isinstance(value, int)`.

Неверный JSON, дополнительные ключи, повтор ключа и неверный тип отменяют запуск.
Отсутствующее обязательное значение и нарушение бизнес-диапазона отклоняют отдельную строку.
Так программа различает непонятную структуру источника и понятную, но некорректную запись.

## 5. Проверка значений выражениями

`checked_plan` явно задаёт типы столбцов. Дата проверяется по точной записи UTC
и преобразуется в тип Datetime с часовым поясом UTC. Произвольный локальный часовой пояс
не угадывается. В этой модели не требуется решать, какой из двух повторяющихся осенних
локальных часов имеется в виду.

Затем цепочка `when / then / otherwise` присваивает первую причину отказа.
Допустимы коды LOG- с восемью цифрами, три известных сервиса, HTTP-статусы 100…599
и задержки 0…60 000 мс. Явный `fill_null(False)` не позволяет отсутствующему значению
случайно пройти логическую проверку.

Сводка качества содержит только код причины и количество. В ней нет копий исходных
неправильных строк. Это уменьшает распространение лишних сведений, но не делает
настоящие журналы или очищенную таблицу автоматически публичными.

## 6. Дубли и конфликтующие идентификаторы

Из корректных строк выбираются только поля контракта. `unique()` удаляет полностью
одинаковые нормализованные события. После этого группировка по `event_id` проверяет,
не осталось ли у одного кода несколько разных строк.

```python
clean = valid.unique().sort("event_id")
conflicts = clean.group_by("event_id").len().filter(pl.col("len") > 1)
```

Конфликт отменяет сборку. Нельзя выбрать произвольную первую запись: тогда ответ зависел
бы от порядка источников. В отличие от модели заказов с версиями, у запроса этого проекта
нет поля новой версии. Если нужны исправления событий, нужно сначала определить контракт
исправления, а не молча заменять содержимое по совпавшему коду.

## 7. Почасовая агрегация

У очищенной записи появляются `date` и `hour`. Час задаётся усечением даты-времени
до начала часа UTC. Группа определяется парой «час, сервис».
Затем считается число запросов, отдельные количества 4xx и 5xx, средняя задержка,
p95 и число медленных запросов.

Ошибкой сервера считается только 5xx. Ошибки 4xx видны отдельно и не входят в
`error_rate_pct`. Граница медленного запроса включительна: при пороге 200 мс запрос
ровно 200 мс уже медленный. Эти определения нужны до просмотра красивой статистики.

Доля ошибок вычисляется как среднее логического признака, умноженное на 100.
Среднее задержки и p95 округляются для выходной таблицы до двух знаков.
Количество запросов остаётся целым, а сумма почасовых количеств сверяется
с числом очищенных уникальных событий.

## 8. Ручной пример среднего и p95

Пусть в одном часу у api три уникальных запроса:

| Код | Задержка, мс | HTTP-статус |
| --- | --- | --- |
| LOG-00000001 | 100 | 200 |
| LOG-00000002 | 200 | 500 |
| LOG-00000003 | 300 | 404 |

Добавим точную копию первой строки. На входе четыре строки, после удаления дубля — три.
Среднее равно `(100 + 200 + 300) / 3 = 200` мс. Ошибка 5xx одна, её доля — 33,33%.
Ошибка 4xx тоже одна, но это отдельный показатель. При пороге 200 мс медленных запросов два.

Для p95 в проекте выбрана линейная интерполяция. В отсортированном наборе из трёх
значений индекс равен `(3 − 1) × 0,95 = 1,9`, если нумеровать с нуля.
Это 90% пути от 200 к 300, то есть 290 мс. Другое правило квантиля может дать 300 мс;
поэтому слово p95 без названия метода не определяет точный ответ для маленькой выборки.

Нельзя усреднить почасовые p95, чтобы получить суточный p95. В обзоре по сервису
показатель снова считается по очищенным запросам этого сервиса, а не по готовым перцентилям.
Ручной пример закреплён автоматической проверкой.

## 9. Разделы Parquet и дата в пути

Очищенные события распределяются по папкам вида `events/date=2026-10-01/part.parquet`.
Parquet хранит типизированные столбцы и использует сжатие Zstandard.
Дата раздела не повторяется в каждом выходном событии: при чтении набора можно получить
её из пути через `hive_partitioning=True`.

```python
events = pl.scan_parquet(
    "workspace/output/events/**/*.parquet",
    hive_partitioning=True,
)
```

Выбор UTC важен: запрос в 23:59:59 и запрос в 00:00:00 следующего дня относятся
к разным разделам. Для бизнес-даты по часовому поясу клиента понадобилось бы другое
явное правило, а не только изменение подписи папки.

Разделение не делает каждый запрос быстрее. Если читать все даты без фильтра,
движок всё равно должен обработать нужные файлы. Кроме того, очень много маленьких
файлов может ухудшить работу. Здесь один файл на дату и предел 366 дат — учебное упрощение.

## 10. Пересборка и восстановление

Исходный набор хэшируется до обработки и ещё раз перед заменой результата.
Если содержимое изменилось, новая выгрузка не публикуется. В манифест сохраняются
хэши содержимого, версия Polars, итоговые показатели и контрольные суммы выходных файлов.
Абсолютные пути источников туда не записываются.

Новая выгрузка сначала создаётся в отдельной временной папке. До её готовности прежняя
папка результата не меняется. При замене старая временно переименовывается в резервную;
если следующая операция переименования не удалась, она возвращается обратно.
В тестах проверяются ошибка записи Parquet и отказ именно второго переименования.

Это не общая транзакция файловой системы. Авария процесса между операциями может
оставить резервную папку; постоянный внешний читатель может заметить короткий разрыв.
Одновременные писатели не поддерживаются. Мы гарантируем проверенное восстановление
после обычных исключений, а не промышленную отказоустойчивость на любой ОС.

## 11. Что проверить самостоятельно

После установки зависимостей выполните:

```sh
python -m logs_pipeline demo
python -m logs_pipeline run
python scripts/smoke_check.py
python -m unittest discover -s tests -v
```

Стандартное демо даёт 10 000 уникальных запросов, 100 дублей, пять отклонённых строк,
три даты UTC и 150 почасовых групп. Ошибок 5xx — 500, ошибок 4xx — тоже 500.
Повторная сборка должна сохранить эти количества, а не удвоить их.

Генератор использует фиксированное начальное значение, поэтому можно сравнивать
поведение реализации на одинаковом наборе. Нельзя выдавать такой набор за измерение
производительности настоящего сервиса или делать из него вывод о его доступности.

## 12. Разработка и разобранные риски

Базовые проверки обработки прошли при первом запуске. При дополнительном просмотре
обнаружено важное свойство стандартного JSON-декодера: повтор одного ключа обычно
перезаписывает прежнее значение. Если два читателя иначе трактуют такой объект,
проверка и обработка могут разойтись. Поэтому добавлен строгий обработчик пар ключей
и проверка отклонения повторного `duration_ms`.

Также отдельно проверяются тип bool вместо числа и JSON-константы NaN/Infinity.
Не следует заменять строгую проверку входа на «попробуем преобразовать всё, что получится»:
так меняется договорённость с источником. Выбор между отказом пакета и карантином строки
должен быть виден в документации и тестах.

## 13. Ограничения и следующий шаг

Максимум — 100 JSONL-файлов, 8 МиБ на файл, 32 МиБ суммарно и 100 000 записей.
Это защитные ограничения небольшого проекта, не опубликованный результат нагрузочного теста.
Проверены Linux и локальные примеры; Windows описана в настройке CI, но удалённый запуск
не состоялся. Стандартный бинарный пакет должен поддерживать используемый процессор.

Следующий шаг — измерить память на нескольких контролируемых размерах и сравнить
полный снимок с инкрементальным вариантом. После этого можно обсуждать потоковую запись
разделов, хранилище контрольных точек или расписание. Сначала нужны требования,
а не установка большой платформы ради количества технологий.

## 14. Вопросы для собеседования

**Чем LazyFrame отличается от DataFrame?** Первый описывает вычисление, второй содержит
полученную таблицу. Важно показать, где выполняется collect и возникает результат в памяти.

**Почему p95 не равен максимальному времени?** Это выбранный квантиль распределения,
в проекте с линейной интерполяцией. Для 100, 200 и 300 мс он равен 290 мс.

**Почему нельзя складывать результаты повторных запусков?** Каждый результат уже
представляет весь текущий входной набор, а не новую порцию событий.

**Что защищает от неполной выгрузки?** Подготовка во временной папке и восстановление
прежнего результата при обычном отказе замены. Полной файловой транзакции нет.

**Чем дубль отличается от конфликта?** Дубль повторяет все нормализованные значения;
конфликт повторяет только код события и меняет содержимое.

## 15. Упражнения

1. Измените порог медленного запроса с 500 до 1000 мс. Число запросов и доля 5xx
   должны сохраниться, а медленных запросов не должно стать больше.
2. В отдельном синтетическом наборе повторите запрос с другим `duration_ms`.
   Ожидаются конфликт и неизменность прежнего манифеста результата.
3. Уберите один входной файл и пересоберите снимок. Объясните исчезновение соответствующих
   событий и почему это отличается от журнала накопительной загрузки.
4. Самостоятельно пересчитайте ручной пример из раздела 8; проверьте 200 мс среднего,
   290 мс p95, две медленные строки и одну ошибку 5xx.
5. Предложите изменение схемы для кода окружения, например test/prod. Определите,
   какие ключи группировки и какие проверки нужно обновить, прежде чем менять код.

## Проверка переносимости перед публикацией

GitHub Actions сначала обнаружил ошибку YAML: двоеточие перед пробелом внутри команды
установки пакетов требовало кавычек вокруг всей команды. Затем Windows выявила
зависимость тестов от системной кодировки: чтение текстовых результатов исправлено
на явный UTF-8. Такие ошибки не видны при проверке только на Linux.
Кроме того, преобразование UTC-столбца Polars в объект datetime Python на Windows
требует базы часовых поясов. Добавлен закреплённый пакет tzdata. Тест с ручным расчётом
метрик материализует такую строку и тем самым проверяет этот путь.
Отдельно исправлен вывод вспомогательных команд: при перенаправлении stdout на Windows
системная кодировка могла не поддерживать кириллицу. Все команды теперь явно выбирают
UTF-8. Добавлен тест с принудительной кодировкой cp1252, проверяющий эту регрессию.
